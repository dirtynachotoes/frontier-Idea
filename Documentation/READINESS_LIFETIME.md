## Source inspection and its limits

Reviewed actual pinned sources (not guessed engine behavior):
- player/player_position.cpp: observe() discovers an owned component on physics sync, publishes from known components, and does not invalidate a prior snapshot on a failed body read. poll() runs on camera frames, falls back to teleport::local_player_component(), clears component and present on failed ownership, otherwise refreshes while preserving the snapshot on a body-read failure. reset() clears both. snapshot() reads the published finite candidate under the existing seqlock; Frontier separately checks finiteness.
- hooks/teleport/teleport_move.cpp: owns_local_player() requires a component and installed controlled-handle accessor. owns_player() returns false if the accessor returns kInvalidHandle, the fault-safe owner read fails, or masked owner/controlled indices differ. local_player_component() is the teleport feature's cache, populated by apply_pending() only while its feature is active. The position abstraction's physics observer therefore remains necessary. clear_targets() withdraws the accessor/cache during hook teardown.
- hooks/teleport/teleport_lifecycle.cpp: physics_sync() observes position; camera_transform() polls position then bootflow world/slice before the existing patched Frontier tick. Position reset is part of hook uninstall. The ordinary physics sync can stop at rest, which is why snapshots and frame polling exist.
- hooks/bootflow/world_step.cpp: in_world() requires the published step 38 and a timestamp younger than the existing 1,000 ms stale bound. Camera frames publish the sampled step immediately before Frontier. Activity/load changes can change the step; source does not prove the engine's returned step/controlled handle in this particular runtime session.

These prove possible invalidation paths, not which path actually occurred. Fresh native heartbeat and a roughly two-second interval do not identify an ownership loss, world-step change, snapshot loss or the exported host-ready gate. No source-backed root cause is established, so this build contains diagnostics only. No cache retention, ownership, timeout, activity ID, thread or lease behavior is changed. No exact two-second lifetime-fix regression is claimed.

## Diagnostic interpretation

The native-owned reserved uint32 at ControlBlock offset 108 now carries readinessBits; the block remains 128 bytes/version 1 and all existing offsets/names and Spatial V2 fixtures are preserved. Bit 31 marks the optional extension. Python status shows ready_in_world, ready_component, ready_ownership, ready_snapshot, ready_finite, ready_combined, ready_host and ready_ownership_checked. Old zero-extension data is unknown/null. Ownership is null when the existing world/component guards prevent evaluation. Combined is Guardian-only; exported ready still also requires host-ready.

The production tick samples the existing snapshot/component once, performs the same guarded ownership call once and uses the diagnostic predicate result as the unchanged Guardian readiness condition. It logs ev=frontier_readiness only when the sampled bits change. Logs include all predicate bits, host gating, resulting readiness, context and tick_ms. Logging records even transitions shorter than the normal 100 ms status publication. If component/snapshot disappear together, poll's documented ownership-invalidating path is a candidate; the fields identify the sampled failed conditions but do not pretend to reveal an engine accessor's internal reason. Further source changes must follow that evidence.
