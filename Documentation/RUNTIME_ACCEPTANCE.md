# One Guardian locomotion acceptance session

Install the one CI candidate using Tools/install_candidate.py with the same actual existing destinations and offline executable fingerprint previously used. Do not paste angle-bracket placeholders. The installer backs up replacements; preserve its backup receipt. Do not install intermediate builds. Existing runtime-validation.json and user configuration remain in place.

1. Start Core with StartGuardianLocomotion.cmd. Load the supported offline Sunrise activity; perform the already-proven normal Guardian movement for 2–3 seconds once to bootstrap the cache, then stop. Ensure existing fly/Scout Link hover are off and existing Anti-AFK is enabled. Choose a clear small flat area. No startup-discovery re-test is requested.
2. Start NMS normally and keep it foreground, on foot in a clear flat area. Press F9 once. Hold W for a short interval, then release. The acceptance criterion is hidden Guardian-authored forward locomotion producing visible NMS motion, followed by a stop. The new log reports queued measured delta and native input_scan_reads; these distinguish an actual Guardian result from a vanilla NMS step. Capture the new locomotion log and native readiness transition only if it fails.
3. In the same session briefly test S/A/D, Shift+W and Space if the corresponding Sunrise authored bindings are configured. Verify motion follows the host's established facing when turning, and jumping reflects a native Guardian result. This does not prove shared terrain collision or free-look camera integration.
4. Press F9 again. Verify ordinary NMS control returns. Stop Core after the session. Do not repeat F8, heartbeat, bridge or Spatial V2 acceptance tests.

If W causes no native input scans or no Guardian displacement, report that as a failed locomotion gate; no fallback speed is applied. This session resolves background authored-input scanning and NMS SetToPosition actuation. No game launch is needed for individual plumbing edits.
